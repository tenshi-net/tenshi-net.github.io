An Unnecessarily Complicated Framework: my blog pipeline

May 29, 2026 • 1219 words • 6 min
blogging homelab career learning

If you’re reading this blog, chances are that you don’t realize how complicated things are behind the scenes. What looks like a visually-appealing, easy-to-view blog for my career, home lab and tech opinions is actually several Git(hub) repositories publishing markdown files piped in direct from my primary Obsidian vault.

Why did I do it this way, when spinning up something like a WordPress blog would’ve been so much simpler and easier?

Backstory

I first discovered the idea of a blog pipeline going from Obsidian to a Hugo blog because of one of my favorite tech content creators, NetworkChuck. In his video, he runs through his own blog pipeline. He set it up with a Python script that takes notes from a dedicated folder in his Obsidian vault, syncs them into his Hugo blog repository, then Hugo turns those markdown files and converts them into posts on the blog. The blog is then pushed to an external hosting provider.

I wasn’t interested in the last step. I don’t have a whole lot of money to spare at the moment and paying for a third-party host seemed like an unnecessary step when GitHub Pages exists for free without any sort of annoying freemium limitations.

Little did I know that was a bit more complicated than I originally realized. Back in November 2025, I tried following Chuck’s video, just stopping shy of the part where it pushes the blog to the external provider. Unfortunately for me, several hours of working on getting things set up ended up being a waste of time because, for the life of me, I could not get the site to publish to GitHub Pages. It tried once, but failed the moment I tried to further edit the site (and I wasn’t doing anything extreme, just text editing).

That level of miserable, time-wasting failure was too much for me at that point in time, as I was dealing with particularly strong discouragement from my career woes that made me come very close to giving up on the whole tech career journey I’ve been trying to walk.

Another go

Because of that discouragement, I shelved this project for a few months. Once I had gotten to a better state of mind, I decided to return to it in late April of this year (2026). This time, I followed a different guide that was specifically made for hosting a Hugo site through GitHub Pages. I then blended the steps from Chuck’s video for syncing my Obsidian notes to the blog so that I could still maintain that all-in-one organization of using Obsidian for the blog rather than having to copy-paste things.

I didn’t go the route of using a Python script for automation like Chuck did. I might consider doing that at some point but for now, I have things working as intended and I don’t want to mess around with it too much without better learning why the original attempt failed so much.

Start to finish

My workflow goes like this.

I have an Obsidian vault titled TenshiNet HQ. I treat this vault like an information headquarters, thus the name. In this vault, I hold a majority of my written content, from blog posts to project brainstorming to home lab documentation and so forth. In the Blog Desktop folder, I organize my posts by year and month, with a separate folder for different drafts. I write each post using markdown, ensuring that the beginning of each post has appropriate metadata in order to list the correct date, a more detailed title, tags, etc.

I also have a completely separate folder apart from Blog Desktop called “posts” (the only lower-case folder in the vault). That’s where I place posts that are meant to be published to the blog. When I finish a post in the Drafts subfolder, I clone it within Obsidian and move it over to the “posts” folder.

From there, I use rsync to sync that folder with the appropriate folder within my Hugo local Git repository. Once the sync is finished, I then navigate my terminal over to the root directory of said repository and I add and commit the change to the local repository. Following that, I run the hugo server command to proofread and view the post in a live-like setting.

From there, the content has to be uploaded to GitHub. First off, there are actually two GitHub repositories related to the blog: one simply titled blog and the other is titled tenshi-net.github.io, the proper formatting for a GitHub Pages repository. The blog repository stores the code locally on my system, while tenshi-net.github.io is where the blog is deployed to. This is done through usage of a Git submodule which functions as a reference back to the blog local repository. In other words, the files from the local blog repository will publish under the tenshi-net.github.io repository on GitHub proper without any added effort.

I actually use GitHub Desktop to manage all of my GitHub repos. I do know the basics of how to use GitHub within the terminal but I’m still quite new to Git and GitHub, so the the desktop application makes it way easier to manage and understand what’s going on. Once I’ve checked the new post with the hugo server command, I go into GitHub Desktop and I push the updated blog to the tenshi-net.github.io repository.

From there, it’s just a matter of waiting for GitHub to build and deploy the site accordingly!

Why the complications?

I swear I didn’t do this because I enjoy complications or stress. Quite the opposite, in fact. No, I did things this way because I wanted to push myself. I liked the concept of this project, and I wanted to see if I could do it properly. Before, I did actually use WordPress as my blog host, but its freemium restrictions were irritating and it just felt like it was a lot more than I needed for just hosting a basic blog for discussing my home lab, career and tech opinions. By going this route, I would be pushing myself to better learn Git(Hub) and Hugo. I’m still pretty green with both, I’m not confident I could break out of the current setup without a lot more learning, but it’s a start.

Not only this but eventually, I can use the blog as literal proof of ability. I can consider it a technical project if it would be beneficial to talk about it with future job applications. I also think that doing things this way tells people that I’m not a poser: I may not be amazing at anything specific, but I do my research, I learn new things, and any time I ‘give up’, it’s merely a temporary tactical retreat until I can return with a better mindset and a new frame of mind.

Do I recommend most people go this route? Not really. Unless you are patient, know how to fill in the gaps on guides/walkthroughs, and want something technical to point to on a resume, you probably would have it better using a website builder tool such as WordPress or Weebly instead. But for those who decide to try this project, it can truly be a learning experience that gives you a space to get your thoughts and project documentation into the world!
