Network Nightmare [Troubleshooting Tales #1]

May 28, 2026 • 1172 words • 6 min
linux homelab pc troubleshooting troubleshootingtales

In over eight months of using Manjaro Linux as my daily driver, I’ve encountered a handful of oddities and issues that I’ve had to sink a few hours into fixing. By and large, the experience has been smooth, but when something breaks, it seems to break randomly and without immediately apparent cause. I just dealt with another such situation and figured I would write down what I did to fix the issue as part of a new post series I’m starting: “Troubleshooting Tales”.

A dreaded calamity

“I really hope this update doesn’t break,” I muttered to myself as my PC rebooted following the latest Manjaro update. There wasn’t any specific reason I had that feeling of dread. The update process appeared to go perfectly well. I always follow Manjaro’s recommended steps before an update to minimize breakage and things looked good. I even always uninstall my AUR applications before each update, reinstalling them after the update finishes. Typically, the updates go smoothly that way.

Upon rebooting, I noticed my VPN wasn’t able to connect to any servers. I disabled the VPN connection and then realized I wasn’t able to get any wi-fi connection whatsoever. I have a somewhat unique setup in that I can’t get an ethernet connection to my PC, so I have to resort to USB wireless adapters. My current setup runs a USB extension cord from my desktop and into the nearby hallway with my adapter and antenna propped up. It’s a very rough and rugged setup but it’s what I had to do. Remember my lack of wi-fi capabiilities, it comes back around.

I tried the typical troubleshooting process:

  • sudo systemctl restart NetworkManager
  • systemctl status NetworkManager
  • Reseating the wi-fi adapter and its extension cable
  • Rebooting the PC
  • Booting into an older kernel version

None of that fixed the issue. According to the NetworkManager status, everything was fine. Nmcli and dmesg told a different story.

Worse than expected

I’m not a Linux pro but I generally know how to troubleshoot it. I did some research and ran some things through AI and was led to run some more commands.

First, I tried these two commands to check the interfaces:

ip link show
nmcli device status

These showed me that the wi-fi adapter wasn’t even recognized whatsoever. My first assumption was that it was a driver issue of some sort. Turns out, I was on the right track. I investigated further with dmesg (aided by AI for the full syntax):

dmesg | grep -E 'wifi|wlan|firmwar|error' | tail -100

That command gave me a good look at error messages that indicated some sort of firmware corruption related to the drivers. What’s strange is that I actually encountered something similar with a Raspberry Pi 4 that I’m working on for a future project. Fortunately, the events of today ensure I’ll have better luck at solving that issue at some point in the future, but I digress.

Everything I read, both online and through AI, suggested that I needed to reinstall the linux-firmware package using Pacman. The problem? How was I supposed to connect to the internet if my only means of doing so (wi-fi) was out? This required a micro adventure of further research to learn alternate ways to connect without ethernet or traditional wi-fi. If I couldn’t get some sort of connection, my only other option would’ve been to download the packages I needed and use a USB thumb drive to transfer from my laptop to my PC, manually reinstalling things. That would likely be a hunt and a much longer process.

An alternate path

That’s when I read about mobile USB tethering. I was aware of mobile hotspot tethering and Bluetooth tethering but was not aware of USB tethering. In essence, this allows you to hook your phone up to your PC via a USB cord and this allows the PC to effectively believe it’s connecting through a wired ethernet connection when, in reality, everything is routed through your phone’s wi-fi.

As always, though, it wasn’t that simple.

The cord I usually charge my phone with is a three-in-one. It has USB-C, microUSB and Apple Lightning heads and those attach to a USB-A male that you can either plug into a PC or a power pack. I didn’t realize that it was designed as charge-only, as I never really transfer things to/from my phone via a cable, opting for options like cloud or KDE Connect instead.

Luckily, I was able to find a USB-C to USB-A cable that would work. I had to enter Developer Mode on my phone to toggle some settings but once I did, this cable allowed the USB tethering process to work as intended.

A swift solution

Once I was able to connect again, I was able to fix the issue very quickly.

Step 1

Update and reinstall the firmware. To be on the safe side, do a full sync.

sudo pacman -Syu linux-firmware

Step 2

Now, reload your drivers using modprobe.

sudo modprobe -r [driver name]
sudo modprobe [driver name]
Note

You’ll need to do your own investigation on the vendor and model of your wireless adapter. You can use a command like inxi -Nxxxz to find this information.

Step 3

Restart NetworkManager again.

sudo systemctl restart NetworkManager

Step 4

By now, you should see your system reconnecting to your hotspot but if not, try rebooting. Once you reboot, everything should be working as intended.

Context and reasoning

As it turns out, the reason this whole issue occurred was because I removed the AUR packages before updating. The Manjaro community forum mentioned that there’s a meta package meant for supporting older, out-of-date kernels and that this package was dropped in favor of the relevant Arch packages. When I removed the AUR packages, it also removed this meta package, which contributed toward the issue I had.

As community members have told me, packages can be marked as ‘foreign’ (which would get caught in the AUR removal command) because of name changes or another package replacing them, which means that removing via the AUR can lead to breakage by removing system-critical files.

It’s wild to me how Linux can be so simple, yet so strange at the same time. I would never have guessed that’s what happened if not for the fact that I did see linux-firmware-meta listed among the alien packages in the Pamac foreign package list I save before every update.

As I said before, I have a similar problem with a Raspberry Pi 4. Not because of an update, but it happened after I flashed the microSD with the distro I’m planning to use on it. Due to this relatively frustrating breakage, I’ve not only learned a bit more about my daily driver distro but I’ve also learned some of the process of how I can repair the firmware on the Pi and get back to the project I had planned for it.

The world of tech is constantly interconnected. Never underestimate what you’re learning every time you try to fix something that’s broken!
